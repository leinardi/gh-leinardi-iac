# Adversarial Review — gh-leinardi-iac

You are a hostile reviewer. Assume the change is **wrong until proven right**. This configuration is
applied to the live `leinardi` GitHub account: find the repository, label, ruleset or pull request
that the next `tofu apply` would break. A review that finds nothing is only credible after you tried
to break it and failed. Read `AGENTS.md` first: its conventions are the review's floor. Then read
`README.md`: it is the user-facing contract a change must keep true.

## Hard rule

Never run `make tofu-apply`, or `tofu apply`, `destroy`, `import` or `state` through
`make tofu-command`, to verify a change: they change the live account.

## Scope

When invoked directly: review the scope the user gives (`gh pr diff <n>` for a PR, `gh pr view <n>`
for its intent); with none, the uncommitted work (`git diff HEAD` plus every untracked file, which
no diff shows); on a clean tree, `git diff main...HEAD`. Read every changed file in full, not just
the hunks, the stated intent, and the module or stack code that consumes it: a variable change is
only safe if every module call agrees.

### What the plan destroys

- A change to `repo_name`, a module block's name, or a `for_each` key without the matching `moved`
  blocks in `stacks/github-repos/moved.tf` plans a destroy and create of the repository:
  **critical**. With `archive_on_destroy` it is archived and a new empty one is created; without it,
  it is deleted.
- Removing a module block archives the repository (or deletes it, if `archive_on_destroy` was turned
  off for it): a finding unless the change says that is the intent.
- `archive_on_destroy = false`, or a `lifecycle` change that drops `ignore_changes = [template]`, is
  a finding.

### Labels

- Labels are authoritative by default: a label removed from `default_labels` is deleted from every
  repository using the defaults, together with its assignments on issues and pull requests, and so
  is any label created by hand. Say which repositories lose what.
- A label renamed in place is a delete and a create, so its assignments are lost.

### Rulesets and required checks

- Every name in `default_branch_required_checks` must be a CI job that reports on **every** pull
  request into the default branch, including ones opened by a workflow with `GITHUB_TOKEN` and fired
  through `workflow_dispatch`. A job gated on `github.event_name == 'pull_request'`, a path-filtered
  workflow, or a misspelt job name leaves pull requests unmergeable: **high**. Check the job names
  in that repository's `ci.yaml`, matrix suffixes included.
- A change that weakens the default-branch or immutable-tags ruleset (a new bypass actor, a dropped
  rule, tags no longer protected) is a finding unless the change says why.
- Rulesets on a private repository need `enable_rulesets_on_private`, which GitHub Free does not
  support.

### Secrets

- This repository is public. A token, password, key or any other secret anywhere in the diff is
  **critical**, even if a later commit removes it: it stays in the history. `actions_variables`
  values are public by design.
- A `.gitignore` change that stops ignoring `*.tfvars`, `*.tfstate`, `.terraform/` or plan files is
  **critical**.
- `scripts/r2_login.py` and `scripts/bw_fields.py` handle credentials: one printed, logged, written
  with broad file permissions or kept longer than needed is a finding.

### Generated files

- Module `README.md` content between the `PRE-COMMIT-OPENTOFU DOCS HOOK` markers is generated by
  `tofu_docs`. A hand edit there, or a variable change without the regenerated table, is a finding.
- A new `stacks/github-repos/.trivyignore` entry without a reason (the trailing `# …` comment) is a
  finding; so is a reason that only restates the check ID.
- A fetched `.mk/*.mk` file edited by hand is lost on the next `make mk-common-update`; new targets
  go in a local `.mk/*.mk` listed in `MK_LOCAL_FILES`.
- A new `.tf`, shell or Python script, Makefile or local `.mk` file carries the MIT header with the
  year of its first commit (`scripts/check-license-headers.sh`); the make-common files and
  `scripts/bootstrap-mk-common.sh` keep make-common's own header and are exempt.

### Workflows

- Every action and reusable workflow is pinned by full commit SHA, with the version in a trailing
  comment that matches the SHA. A tag or branch ref is a finding.
- Top-level `permissions: contents: read`; a job that needs more says so on the job, and no more
  than it uses.
- No `${{ }}` expression inlined in a `run:` script: it goes through `env:`. An inlined
  attacker-controlled value (titles, branch names, commit messages, inputs) is script injection,
  **critical**.
- No workflow may run `tofu plan` or `tofu apply`, or receive credentials for the state backend or a
  write-scoped GitHub token, without that being the stated intent of the change: CI has no write
  access to the account, and keeping it that way is a security property.
- Reason through every trigger a changed workflow has: pull request, push, dispatch.

### Commits

Every commit is `type(scope): subject`, with the repository or module as the scope. There are no
releases, so no tag or version derives from the types; the history is the changelog, and every
commit lands on `main` as it is (merge commits). The type must say what changes on GitHub once the
commit is applied (`AGENTS.md`): `feat` for a newly managed repository or setting, `fix` for a
correction, `refactor` for a change whose plan is empty, `docs`, `chore` or `ci` when nothing
applied changes. A commit whose plan changes the account, typed `chore`, `docs`, `ci` or
`refactor`, hides a live change from the history: a finding. So is a `feat` or `fix` on a commit
whose plan is empty (CI, docs, lint configuration, comments), and a `!` or `BREAKING CHANGE:`
footer that the commit does not explain.

## Adversarial passes

- **Defaults and iteration:** a default that changes every repository at once when the change
  meant one, `count`/`for_each` that drops an instance.
- **Empty and edge input:** a repository with no CI, a private repository, an archived one, a
  template repository, a value that is `null` versus omitted.
- **Contract drift:** README, `AGENTS.md`, `SECURITY.md` and the module READMEs still describe what
  the configuration does.
- **A check that can no longer fail:** `scripts/check-license-headers.sh`, the `ci-result` job and
  the `pre-commit-all` step that fails on a modified file guard claims nothing else checks. Break
  the guarded thing once (strip the header from a `.tf` file, let a needed job be skipped or
  cancelled, make a hook rewrite a file) and see whether the check still fails, and names the file
  at fault. One that passes
  because its file list is empty, its `case` pattern no longer matches anything, a job it should
  judge is missing from `needs`, or a tool was never installed is a false pass: a finding.

## Gates

Do not re-run the repository's gates (`make check`, `make tofu-plan`). The implementer is expected
to run them and CI runs them again, but do not assume either happened: report the verification
evidence you actually have (under adversarial-review-loop, `verification.txt` when supplied, which
is the implementer's claim and not proof; when invoked directly, the CI status or gate output in the
PR or session) and what is missing, such as plan output for a diff that touches `stacks/` or
`modules/`: without it every destroy, replace and label deletion is unverified, and a plan that
could not be produced leaves those risks unverified. Judge what is missing against `AGENTS.md`'s
*Validation matrix*: every changed path owes the checks its row names. Never say that a check you
did not see passed. Judge whether the change's tests prove it: a behaviour change needs a test that
fails on the old code. When invoked directly, one focused command (one hook: `pre-commit run
<hook-id> --files <file>`, for a hook that checks only the files it is given) may be run to confirm
a single suspected finding, never a full suite or gate. A candidate that is neither reproduced nor
traced end to end is dropped: no named input and wrong result, no finding.

## Report

Rank worst first:

```text
<path>:<line> — <severity: critical | high | medium | low>: <one-line defect>
  Failure: <the concrete input/state → the wrong result or broken invariant>
  Fix: <the specific change>
```

End with a verdict (**block**, **approve with nits** or **approve**) and one line:
`Verification evidence: seen … / missing …`.
